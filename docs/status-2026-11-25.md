## 2. 85 根因分析（2026-11-24 下午的完整链条）

### 2.1 内核诊断结果
主缓存（557,056 B，codeLimit 540,672 = 33×16 KiB）**只有 block 32 哈希不匹配**。块 32 = 文件偏移 0x80000–0x84000，**code 区最后一块**（540,672 = 8×64K + 16K —— 最后一个小 I/O 正好 16 KiB）。

### 2.2 原版对照（Apple 真机数据，cache-compare v3/v4）
在 GitHub runner 上用 QPRS-6 的脚本解密 22H374 IPSW 的 `Cryptex1,SystemOS`：
- 原版主缓存：**557,056 B，sha256 `e901979f7f1c51ce31a9e7a68d218aa394bc7134aba2f474e9ae6daa50e1e4fc`**
- **原版 block 32 head = `6c69622f6c696263...`（ascii "lib/libchannel.d"），tail 96 字节全 0**
- 内核算出的 got / 镜像里搜到的内容都**对不上这个 head**（内核读到的 `data` 十六进制在**整个 11 GB 镜像里 0 次命中**）

### 2.3 生成链验证（cache-compare，workflow 已入库）
`ditto --rsrc --extattr --acl --nopreserveHFSCompression --nohfsCompression --noclone` 复制到新 APFS 后：**sha256 与原版完全相同（IDENTICAL）** → **镜像生成链的复制环节无损**。
（userdata.yml 自 11-17 创建后 QPRS_REF 一直 38ca105d，未变。）

### 2.4 当前最强假说
**UFS 驱动/APFS 对"最后不满 64 KiB 的 16 KiB I/O"处理有 bug**：数据未等待完成/未正确回填，块 32 的 buffer 保留内核内存旧内容（所以镜像里搜不到）。**`boot-ai4-reread.img` 的单块重读就是判据**：
- reread 的 got == exp（重读正确）→ 大 I/O 尾块丢失实锤 → 修复 = cs_native4k 改小 I/O（逐 16K/64K 块读）或修 NativeUfs 完成处理
- reread 与块读相同（仍错）→ 16 KiB I/O 本身有问题
- reread 与块读不同 → 数据不稳定（缓存/竞争）
